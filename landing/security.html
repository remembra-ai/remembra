Security

Your agents' memory, kept on a short leash.

A memory that every agent reads has to be careful about what goes in, who can read it back, and who wrote it. This is how Remembra handles each, what it doesn't do yet, and when that changes.

  1. Redacted

    Keys, tokens and other secrets are stripped out before anything is saved.

  2. Isolated

    Every account's memory is walled off, and project-scoped keys only see their own projects.

  3. Attributed

    Every handoff names the agent, session and time that wrote it, and whether its facts came from git or from the agent.

  4. Open

    The core is MIT-licensed open source. Read it, run it, host it yourself.

Handoffs and briefs

Remembra Relay passes work between agents, so it is built on the assumption that what one agent wrote may be wrong, or may try to steer the next one.

  • Redacted before storage. Every string in a handoff passes secret redaction and the server's PII policy, value by value. A blocked value is replaced with [REDACTED:pii]; a close is never rejected for it.
  • The raw transcript stays on your machine. Close-out reads git and, for Claude Code, the local session transcript, and sends only the facts it pulled out.
  • Briefs are data, not instructions. Everything another agent or tool recorded is wrapped in one untrusted-data block with a fixed preamble. Text inside it cannot close the block.
  • One trust policy for every line. The handoff, inbox messages, status values, linked projects' headlines and recent memories all pass the same check. When recorded text matches prompt-injection patterns (instruction overrides, requests to keep something from you, hidden Unicode characters, including overrides spelled with look-alike or fullwidth letters), the brief shows a LOW TRUST marker and the id to review, not the text. This covers the brief's text and its JSON fields.
  • Commands are flagged, not trusted. Pipe-to-shell installs (also through sudo, env or a shell's full path), download-then-run commands, base64 -d | sh, rm -rf, force pushes, skipped git hooks, permission-bypass flags, reads of ~/.ssh, .env or ~/.claude.json, and links outside your repository (including hosts a download command names without https://, and links that climb out of it with ..) are marked confirm with the user before running. Images (markdown inline or reference style, and HTML <img>) are removed from the brief's text and its JSON fields, so their URLs cannot carry data out.
  • Tool results are framed too. MCP tools that return stored content (recall, lists, the timeline, the inbox, the brief) wrap it in the same untrusted-data block, with the same escaping.
  • Inbox messages are redacted and scored. Secrets in a message's subject, body and metadata are removed before it is saved, and each message keeps its trust score. An inbox message is a request to confirm with you, never an instruction.
  • Graded, not taken on faith. Each handoff gets a health grade computed from its facts (Ready, Ready with warnings, Incomplete, Conflicted or Blocked) with what is missing, such as unpushed commits or tests that were not run. No language model is involved. The facts come from the closing client: unless remembra-relay collected them under a key scoped to that agent, the grade says it rests on facts the agent reported, not verified.
  • Attributed. A handoff closed with a key scoped to one agent is shown as key-verified, and that key cannot write as another agent. Otherwise it is shown as self-declared. An agent's own summary is marked unverified, or contradicted when the facts disagree.

What we do today

Each item links to the code or the doc that does it, so you can check.

  • Redaction on both ends. The relay client redacts secrets before a handoff leaves your machine (relay/facts.py), and the server scans every stored value again for secrets and PII (secret_scan.py, pii_detector.py).
  • Untrusted-data framing of everything agents recorded, in every brief (relay/handoff.py).
  • Key-verified attribution. The agent on a handoff comes from the API key, not from the request (relay/identity.py).
  • Scoped keys. Keys can be limited to one agent, to certain projects and to a role; keys are stored hashed (auth/keys.py, auth/rbac.py).
  • OAuth for the Claude and ChatGPT apps is authorization code with PKCE (S256 only), and you choose which projects a connection may see (connector/oauth.py).
  • Encryption at rest for the vector store: memory content and metadata there are encrypted with AES-256-GCM, and two-factor secrets are encrypted (security/encryption.py).
  • HTTPS everywhere, with the API, dashboard and website behind Cloudflare, on servers rented from Hetzner in the United States.
  • Named subprocessors. Everyone who handles your data is on the subprocessors page, with what they receive.
  • An audit log of sign-ins, key changes and other account events (security/audit.py).
  • Rate limits per plan and per minute, and a burst limit on handoffs.
  • Open source and self-hostable under the MIT license. A self-hosted server keeps your memory on your network and sends us nothing.

What we don't do yet

Most security questionnaires ask about these. The honest answers:

  • No SOC 2 report, and no outside penetration test. Remembra has had internal security reviews only. Cloudflare and Paddle have their own audits; Hetzner's ISO 27001 certificate covers its European data centers, not the US site Remembra runs in. Remembra itself is not audited.
  • No EU data region. Remembra Cloud is hosted in the United States only.
  • The metadata database is not field-encrypted. Encryption at rest covers the vector store; the database that holds account records and a second copy of your notes does not have field-level encryption yet. One encryption key protects the vector store, and it is not rotated yet.
  • API keys don't expire. You revoke them yourself. An agent-scoped key fixes who a handoff is from, but it can read everything the account can; limit reads with project-scoped keys.
  • No SSO or SAML for the dashboard.
  • Backups are not edited when an account is erased. A deleted account is erased automatically 7 days later; the copies of it in backups age out instead (see retention).

Retention and deletion

  • Handoffs and structured checkpoints never expire. They stay on your trail until you delete them or your account is erased. Free-text checkpoints expire after 7 days by default.
  • Notes and memories are kept while your account is open, unless you set an expiry on them.
  • Deleting your account cancels any subscription at once, with no further charges, and ends every session. 7 days later everything the account holds is erased for good: memories, handoffs, inbox, API keys, connections and settings. Until then, email support@remembra.dev to undo it. Backups are not edited; the copies in them age out: the continuous backup keeps 24 hours of history, and the database copy taken before each deploy is kept only until 3 newer deploys replace it. The privacy policy has the rest.
  • Export your memories whenever you want, through the API.
  • No training on your data: we never use what you store to train AI models, and OpenAI, which embeds and enriches it, does not train on API data under its terms.

OWASP top 10 for agentic applications

How Remembra lines up against the OWASP Top 10 for Agentic Applications (December 2025). Remembra is the memory and handoff layer, not the agent, so most rows are partly covered.

RiskStatusWhat Remembra does, and what it doesn't
ASI01 Agent goal hijackPartlyRecorded text reaches the next agent inside an untrusted-data block, and text that looks like prompt injection is withheld. An agent can still choose to follow what it reads.
ASI02 Tool misusePartlyNothing over the Claude and ChatGPT connector edits or deletes memories, and key roles limit what a key can do. The tools on your machine are outside Remembra.
ASI03 Identity and privilege abusePartlyAgent- and project-scoped keys, roles, and PKCE-only OAuth with per-project consent. Keys don't expire yet, and agent-scoped keys can read the whole account.
ASI04 Agentic supply chainPartlyThe code is open, and dependencies are pinned in uv.lock. From 0.16.0, one tagged GitHub workflow builds each release once, with every action pinned to a commit and the build tools pinned by hash. The wheel and sdist go to PyPI by trusted publishing (no stored token) with PEP 740 attestations (Sigstore) that tie each file to that workflow. The Docker image carries build provenance and an SBOM. The Python packages have no SBOM, the files attached to the GitHub release carry no separate signature, and 0.13.2 and earlier have no attestations. SECURITY.md shows how to verify.
ASI05 Unexpected code executionCoveredThe server never runs stored content, and the relay hooks run fixed commands; nothing in a brief is executed.
ASI06 Memory and context poisoningPartlySecrets are redacted, handoff facts come from git rather than an LLM, an agent's summary is checked against them, and facts that don't match their source are flagged unverified. A key with write access can still store a false note.
ASI07 Insecure inter-agent communicationPartlyHandoffs and inbox messages travel over HTTPS, stay inside one account and project, and show whether the sender was key-verified or self-declared. Messages carry no end-to-end signature.
ASI08 Cascading failuresPartlyHooks time out in 10 seconds and never block an agent, AI-provider failures trip a circuit breaker, and running out of credits degrades a save instead of failing it. A wrong handoff can still mislead the next agent, which is why facts and claims are labelled apart.
ASI09 Human-agent trust exploitationPartlyThe brief and the dashboard show where each fact came from and mark agent-written text as unverified or contradicted.
ASI10 Rogue agentsNot coveredThe trail and audit log record what each key did, but Remembra cannot stop an agent on your machine. Crew mode's enforcement is planned.

Crew mode

Crew mode, several agents on one project at once, is not available yet. When it ships, its limits are these: local enforcement coordinates cooperative agents. It cannot stop an agent deliberately working around it on your machine; every bypass is recorded.

Reporting a vulnerability

Report security issues privately to security@dolphytech.com. We aim to reply within 48 hours, keep you updated while we fix it, and credit you when it is fixed if you want. The same contact is in our security.txt.

In scope

  • remembra.dev, app.remembra.dev, api.remembra.dev and docs.remembra.dev
  • The open-source code in remembra-ai/remembra, including remembra-relay, the MCP server and the installers

Out of scope

  • Denial of service, load testing, spam and social engineering
  • Services we use but don't run, such as Paddle, Cloudflare and GitHub: report those to them
  • Findings with no security impact, such as missing headers on pages without sensitive content

Safe harbor

If you make a good-faith effort to follow this page, we will not take legal action against you or ask anyone else to, and we will treat your research as authorized. In return: use only accounts you own or have permission to test, look at no more of anyone else's data than you need to show the problem, and delete it afterwards; don't degrade the service; and give us 90 days to fix an issue before you publish it, or tell us if you need to publish sooner. We don't run a paid bug bounty.
